# Mai (mai-tutor) — Architecture & Context

Deep-dive reference for future sessions/agents working on this repo. Read this before making changes so you don't have to re-derive context from scratch. Product ideas and planning live in `NOTES.md`; this doc covers the code and the reasoning behind it.

## What this project is

A language-learning app that teaches a new language by building on how the person already expresses themselves in their primary language. Instead of textbook vocabulary, the app finds the words and phrases the user actually uses (fillers, reactions, linking words, the way they show feelings) and teaches natural equivalents of *those* in the target language.

The long-term plan (see `NOTES.md`) is a personal phrasebook, a feelings map, practice using the user's own stories, flashcards and a coverage score, all built from one shared **phrase entry** data structure.

**What exists today is a proof of concept for one piece only, the Personal Word List Discoverer** (the owner's name for it, 2026-09-27; use this name when referring to the feature): the user has a casual chat with a scripted friend ("Mai", called "Sam" until 2026-09-26), and the app shows the user's top 100 most-used words. Since 2026-09-27 it lives on its own page, reached from the Cheatsheet; the home page is just Mai's greeting (its study plan and page cards were removed 2026-10-22), and a ☰ menu reaches the other pages. A **Cheatsheet** page (2026-09-27) shows reference word lists, starting with the 100 most common words. Since 2026-10-01 the Cheatsheet's main list is the **user's own words** (from the Discoverer, typed or pasted, or an uploaded file), and a small **Supabase backend** translates words the pre-built files don't have (see "Backend"). A **Journal** page (2026-10-01) holds entries written in the target language, with photos, cut-out stickers and an audio note, corrected by the backend's `check-spelling` function (which-dialect 0.4.0's journal review: a spellchecker plus English-to-Vietnamese, with optional regional and pronoun checks) and a sentence-frames browser. Since 2026-10-22 the user can **sign in** (email + password) and the journal, their words and their settings **sync to their account** (see "Accounts and sync"); signed out, everything stays on the device as before. Otherwise everything runs client-side: no Claude calls yet. Replies never leave the device, except that dictation audio goes to the browser vendor's speech service (see "Dictation" below).

### Backend (`supabase/`, 2026-10-01)
Owner's request: build the "100 most common words you use" list from the Discoverer or from words the user types or uploads. Any word then needs translating, and which-dialect in the browser was measured at ~100 s and 9.5 MB for 3 words (cold CDN files take ~1 s each and a word needs dozens in a row), so the owner chose **"Backend now"** over a bigger pre-built bank or in-browser translation.
- **`translate` edge function** (Deno): `POST { target: 'vi-Southern' | 'vi-Central' | 'vi-Northern', words: string[] (≤ 25, ≤ 60 chars) }` → `{ entries }` in the same shape as the pre-built files. It reads cached rows from `public.translations` (`target, word, version, entry jsonb`; RLS on, no policies, so only the function's service role touches it), translates the rest with `makeEntry` (4 at a time) and upserts them, so **each word is translated once per language for everyone**. Lowercase words with no result are retried capitalized ("sunday" → *Chủ nhật*). Auth: the publishable key (`withSupabase({ auth: ['publishable', 'secret'] })`); CORS added around it.
- **Data from Storage, not the CDN:** every function reads which-dialect's data from the public bucket `which-dialect`, one folder per language and **data package version** (`en@0.1.1`, `vi@0.1.4`; `_shared/data.ts`'s `dataUrl` and `DATA_VERSIONS`), filled by `npm run mirror-data` (`DATA_SETS`, from the published npm packages; ~12k files, ~150 MB; skips existing files). Before the 0.5.0 bump, folders were named after the which-dialect version (`0.1.1/en`, `0.4.0/vi`, …); those are unused and can be deleted. Locally: 10 new words in ~0.5 s, cached words ~0.01 s.
- **`check-spelling` edge function** (2026-10-01, for the Journal; named `check-grammar` until the owner renamed it the same day, since which-dialect's checker became a spellchecker by default; the app's `checkGrammar`, `lib/grammar.ts` and `GrammarCheck` became `checkSpelling`, `lib/spelling.ts`, `SpellingCheck`): `POST { target, text (≤ 5000 chars), checks? }` → which-dialect's journal **`Review`** `{ text (NFC), corrected, sentences[] }` from `createReviewer().review(text, { lang, region, base: 'en', checks })`. **which-dialect 0.4.0** (owner's request 2026-10-01, implementing `JOURNAL_PLAN.md`): the review is a **spellchecker by default**: English words get the region's word (*market* → *chợ*, *ice cream* → *kem*) or are left out (*the*), missing accents are added (*Toi muon an* → *Tôi muốn ăn*, *khong* → *không*), and an English sentence or clause that follows a sentence frame gets the frame's wording (*but it was expensive* → *nhưng mắc quá*). `checks` turns on only the journal's two opt-in checks, `dialect` (*lợn* → *heo* in Southern) and `pronoun-consistency` (*tôi* earlier, *tui* later → *tôi*); other values are ignored. Each sentence has `original`, `corrected`, `changes` (`{ from, to, why, kind }`, `to` empty when a word is left out), `hints`, `frames` (`{ id, en, text }`, which frames the sentence follows; frames no longer change a sentence) and `unchecked` (English with no translation). It also adds each sentence's `words` (its words of several syllables, from `dictionary.segment`, as offsets into `corrected`), and runs `createChecker().check()` with the same rules to give each change `options`, the matching issue's suggestions (matched by rule and word, in order), when there's more than one, since the review keeps only the first. Each option is `{ text, meanings }`: up to 3 senses from `dictionary.lookup` (`{ pos, posName, gloss (≤ 2 definitions), regions? (only when tagged for some regions), labels? }`); English-word options come with no meanings, because the web side shows their Cheatsheet entry. No listener (a journal is written to yourself). Locally ~2.7 s cold, ~0.2–0.5 s warm.
- **`sentence-frames` edge function** (2026-10-01): `POST { target, topic? }` → `{ frames }`, which-dialect's `createPhrasebook().frames({ lang, region, topic })`: each frame's English and pattern for the region with slots open (Southern *{place} ở đâu?*, Central *{place} ở mô?*), its `topic` (journal, feelings, questions, requests, greetings) and `slots`. 34 frames in which-dialect so far.
- **`word-options` edge function** (2026-10-01; batch mode 2026-10-22: `POST { target, words: [≤ 40] }` → `{ results: { [word]: … } }`, 6 words at a time on the server, a word that fails is left out; used by `lib/wordLookups.ts`): `POST { target, word }` → `{ word, accents, synonyms }`, each a `WordOption` (`{ text, meanings }`); the word can have several syllables: the word's own meanings; **the same letters with other accents** (which-dialect's `dictionary.variants`, since 0.5.0: dictionary words only, most common first, up to 5, for words of any length: *hom nay* → *hôm nay*; syllable languages only): a real word with the wrong tone (*muộn* for *muốn*) passes the spellchecker, and this is how the learner catches it; and **synonyms** from the word's first 3 senses (up to 6, often another region's word: *ngô* → *bắp*). ~0.02–0.5 s.
- **`_shared/words.ts`:** `describeWord` (a word's first 3 meanings: part of speech, ≤ 2 definitions, regions when tagged for some regions, labels), used by `check-spelling` and `word-options`; which-dialect is passed in, like `_shared/entries.ts`.

## Architecture of `web/`

### Pages and routing (`App.tsx`, `lib/useRoute.ts`)
Five pages, chosen by the URL hash so refresh and the browser's Back button work without a router library or server config:

| Route | Hash | Page |
|---|---|---|
| `home` | `#/` (or no hash, or anything unknown) | `Home` |
| `discover` | `#/discover` | `Discoverer` |
| `cheatsheet` | `#/cheatsheet` | `Cheatsheet` |
| `journal` | `#/journal` | `Journal` (lazy-loaded, like the Cheatsheet) |
| `settings` | `#/settings` | `Settings` |

`useRoute` reads `window.location.hash` and listens for `hashchange`; navigation is plain `<a href={ROUTE_HREF[...]}>` links. To add a page: add it to `Route` and `ROUTE_HREF` (`readRoute` looks the hash up in `ROUTE_HREF`), then to the switch in `App` and to `MENU_ITEMS`. If routes start needing parameters or nesting, that's the point to switch to a real router.

**Scroll:** `App` scrolls to the top when entering any page except the Discoverer. It deliberately doesn't for the Discoverer, whose own effect scrolls to the latest message (child effects run before the parent's, so a parent scroll-to-top would override it).

**Site menu** (`SiteMenu` in `App.tsx`; owner's request 2026-10-01, replacing the site header with its "✦ Language Helper ✦" wordmark (later "✦ Mai ✦") and ☰ Menu button): a square ☰ button floating in the **bottom-left corner**, fixed while the page scrolls (`.site-menu`, safe-area aware), whose options open **to its right**, from the bottom up: Home, Cheatsheet, Journal, Settings (current page marked `aria-current="page"`), then a greyed-out "Coming soon" list. On the chat page it sits 150px higher, above the reply box; while the journal editor covers a phone's screen it hides. Pages keep 96px of room at the bottom for it. ### Accounts and sync (`lib/sync.ts`, `lib/localStore.ts`, `components/AccountCard.tsx`) (2026-10-22)
Owner's request: "add users to mai-tutor … i want to be able to save my entries". Decisions (owner, 2026-10-22): **email + password** (free; phone + SMS code needs a paid SMS provider such as Twilio Verify, and an emailed link would open in Safari instead of the iPhone home-screen app, which has its own storage), **no confirmation email**, **sign-ups off: just the owner for now** (accounts are made in the Supabase dashboard, Authentication → Add user, "auto confirm"), sync **the journal + my words + settings**, and **upload what a device already has on first sign-in**.
- **Local-first:** every device keeps its full copy (IndexedDB for entries and stickers, localStorage for the rest) and works offline and signed out exactly as before. Signed in, `sync.ts` copies changes both ways. Sign-in UI is the "Your account" card at the top of Settings; signing out keeps the device's copy and stops syncing.
- **Backend (`supabase/migrations/20261022120000_user_records.sql`):** one table, `user_records (user_id, kind 'entry'|'sticker'|'setting', id, data jsonb, changed_at, deleted)`, RLS `user_id = auth.uid()` (checked: another user or the publishable key alone sees nothing). Files (photos, stickers, audio) go to the private bucket **`user-files`** at `<user id>/<sha-256 of the file>` (owner-only read/insert policies): named by content, so a photo used as a sticker too is stored once, and an upload that already exists is skipped. In the JSON, each Blob is replaced by `{ "$file": path }` (`withFilesUploaded` / `withFilesDownloaded` walk any record, so new Blob fields need no sync changes).
- **The sync (`syncOnce`):** reads every row's `kind, id, changed_at, deleted` (small), compares with this device record by record, and copies **whichever side changed later** (last write wins, by the devices' clocks): newer there → download (or delete, for a tombstone); newer here or missing there → upload. So the first sync on a device uploads everything it had. Deletes made here are queued in `mai-tutor:sync-deleted` (`recordDeleted`) and sent as tombstones (`deleted = true`, `data` null). Change times: entries `changedAt ?? updatedAt`, stickers `createdAt` (they never change), settings from `mai-tutor:sync-times`. A setting saved before accounts has no time and counts as 1970, so any real change elsewhere wins over it. After pulling journal changes it fires `JOURNAL_SYNCED_EVENT` (`useJournal`/`useStickers` reload); pulled settings go through `storeApply`, which `useStored` picks up live.
- **When it runs:** at startup (`startSync` from `App`, which loads the Supabase client (~55 KB gzipped, its own chunk) in the background), on sign-in, 2 s after a local change (`onLocalChange`, debounced), when the app comes back into view, and when the browser goes online. One sync at a time; a request during one runs another after it. `useSyncStatus` drives the card ("Everything is saved to your account (synced at …)" / "Couldn't sync … Your changes are safe on this device." + Try again).
- **`lib/localStore.ts`:** the synced localStorage keys (`SYNCED_KEYS`: my words, custom lists, picks, target language, journal extra checks, Discoverer chat) are read and written only through `useStored` / `storeSet` / `storeGet` (a `useSyncExternalStore` hook shared by components and tabs). `storeSet` records the change time and skips writes of an unchanged value. Pages no longer save in a `useEffect` on mount: a write on mount would stamp a default value as a fresh change and overwrite the account's real data on a new device.
- **Supabase client:** `supabase()` in `lib/backend.ts` (lazily imported `@supabase/supabase-js`; the session lives in localStorage). Edge-function calls still use plain `fetch` with the publishable key.
- **Tested** (Chrome, local Supabase, a throwaway local user): wrong password → "Wrong email or password."; first sign-in uploads a pre-account entry (photo + audio), a sticker and two settings (photo and sticker deduplicated to one file); a wiped browser signing in gets it all back with working Blobs, and the language radio updates live; a local language change and a sticker delete reach the table; an edit made directly in the table (newer `changed_at`) is pulled and shows on the open Journal page.
- **Known limits:** last write wins per record (two devices editing the same entry offline: the later save wins whole); files of deleted entries stay in Storage (no cleanup); signing in as a different account on the same device would merge that device's data into it; no password reset in the app (do it from the dashboard); sign-ups and the confirmation email are set in the Supabase dashboard for the hosted project (`supabase/config.toml` has `enable_signup = false` for local).

### Discoverer screens and state (`pages/Discoverer.tsx`)
Two views inside the page, switched by a `view` state (`'chat' | 'results'`). Both show a "Personal Word List Discoverer" eyebrow above the heading. The view isn't in the URL, so leaving the page and coming back always opens the chat (with the conversation intact).

**App state** is a single `SavedState` object:

| Field | Meaning |
|---|---|
| `replies: string[]` | The user's sent replies. `replies[i]` answers `MAI_SCRIPT[i]`. |
| `draft: string` | The current unsent text in the reply box. |

It's kept with `useStored('mai-tutor:chat')` (`lib/localStore.ts`), saved on every change, so a refresh doesn't lose the conversation; it syncs to the account like the other settings. Storage is a convenience and the app works without it (values then last until a reload). **Start over** confirms with `window.confirm`, then resets to `EMPTY_STATE`.

**Chat screen** (`Discoverer`):
- Renders `MAI_SCRIPT.slice(0, replies.length + 1)`: every Mai line already answered, plus the next line waiting for an answer. Each line is a `.turn` containing Mai's bubble and, if present, the user's reply bubble.
- There is no separate message list. The conversation is fully derived from `replies.length` and the script, which is why Mai's lines can't depend on what the user said.
- `finished` is `replies.length >= QUESTION_COUNT`. When true, the reply box is replaced by a **See my top 100 words** button. Mai's final line (the goodbye) is shown but never answered.
- Reply box: `<textarea>` with `autoCorrect="off"`, `autoCapitalize="off"`, `spellCheck={false}` so slang and fillers aren't "fixed". Enter sends, Shift+Enter adds a newline, and `isComposing` is checked so Enter during IME composition (e.g. typing Japanese) doesn't send.

- Auto-scrolls to the bottom (`bottomRef`) whenever a reply is added or the view changes.

**Results screen** (`Results`):
- `topWords(replies, 100)` produces the list. Also shows reply count and total words (via `tokenize`).
- Real words show a bar scaled to the top count. Suggested (fallback) words are greyed out with a "suggested" label and no count.

### Mai's script (`conversation.ts`)
`MAI_SCRIPT` is a fixed array of 14 lines. The first 13 each expect a reply; the last is a goodbye (`QUESTION_COUNT = MAI_SCRIPT.length - 1`). ### Word counting (`wordCounts.ts`)
- `tokenize(text)` — converts curly apostrophes (`‘ ’`) to `'`, lowercases, then matches `/[\p{L}\p{N}]+(?:'[\p{L}\p{N}]+)*/gu`: runs of letters/digits, with inner apostrophes allowed so "don't" and "I'm" stay single words. Unicode-aware, so accented letters work. Hyphenated words split ("kinda-sorta" → two words), and numbers count as words.
- `topWords(texts, limit = 100)` — counts every token across all replies (**every word counts**: nouns, fillers and common words included), sorts by count descending then alphabetically, and takes the first `limit`. If that's fewer than `limit`, it tops up from `FALLBACK_WORDS` in list order, skipping any word already present, marking these `suggested: true` with `count: 0`.
- `FALLBACK_WORDS` — a fixed list of 100 everyday words **supplied by the project owner**. Keep it exactly as given (order and contents), including its few nouns (Person, Friend, Time, …); changes to it should come from the owner. It's also recorded verbatim in `NOTES.md`.
- `displayWord(word)` — words are stored lowercase; this capitalizes "i" and "i'm"/"i've"/etc. for display.

### Dictation (`useDictation.ts`)
The notes originally planned to rely on the phone keyboard's built-in dictation (no in-app button). Desktop browsers don't have that, so a **🎤 Dictate** button was added using the Web Speech API (`SpeechRecognition` / `webkitSpeechRecognition`).

- Supported in Chrome, Edge and Safari; not Firefox. `dictationSupported` is checked once at load; unsupported browsers see a note suggesting another browser or OS dictation (on a Mac, press Fn twice).
- Minimal Web Speech API types are declared in the file because not every TypeScript `lib.dom` includes them.
- Settings: `continuous = true`, `interimResults = true`, `lang = navigator.language`.
- In-progress speech is exposed as `interim` (shown in grey italics above the reply box). Each finished phrase is passed to `onFinal`, which the app **appends to the end of the draft**, not at the cursor.
- `onFinal` is kept in a ref updated in an effect (not during render; oxlint's `react(refs)` rule flags that).
- Errors: `not-allowed` → "Microphone access was blocked."; `no-speech` and `aborted` are ignored; others are shown.
- Dictation stops when the user sends a reply, when the view changes, and on unmount, so speech never lands somewhere unexpected.
- **Privacy caveat:** Chrome sends the audio to Google's servers for recognition (free, but not on-device). Safari uses Apple's service.
- Browser recognition, like keyboard dictation, usually drops "um"/"uh", which is why the filler chips remain.

- No tests. The word counting in `wordCounts.ts` is the most test-worthy logic if tests are added.
- Browser-tested by an agent (2026-09-27, Chrome): home page, menu, the Cheatsheet page, checking a to-do (persists after navigating), opening the Discoverer, and Back. Sending replies, dictation and the results screen haven't been click-tested by an agent.

## Considered but not built

- **Standalone prompt list** (2026-09-26): the first POC showed 20 prompts one at a time in random order, grouped by emotion/situation (Everyday, Annoyance, Excitement, Opinions, Storytelling, Social, Stress). Replaced by the Mai conversation at the owner's request because a conversation feels more natural. The Mai script covers the same topics.
- **Excluding nouns from the top 100** (2026-09-26): built with the `compromise` library (rule-based English part-of-speech tagging that runs in the browser; it correctly tagged "work" as a noun in "work was fine" and a verb in "I work too much"). Reverted the same day when the owner decided nouns should be included. `compromise` was uninstalled: it added ~140 KB gzipped and nothing else used it. It could come back for grouping word forms ("want"/"wanted") or finding phrases ("you know", "I mean"). It's **English-only**, which matters if users' primary language isn't English.
- **Hiding very common words** ("the", "a", "is") behind a toggle: offered, but the owner chose to show everything, since common words like "like", "so" and "really" are exactly what the app wants to catch.
- **AI-written Mai replies**: Mai reacting to what the user actually said, via Claude. Deferred to keep the POC free and backend-free. This is the natural next step for making the chat feel real (and matches `NOTES.md`'s "AI follow-up questions").
- **Custom font**: the owner shared a screenshot of another site (Try Studio) whose soft serif looked like Fraunces or Recoleta; switching the app to Fraunces was offered but not requested. (Superseded 2026-10-07: the app uses Playpen Sans, see Styling.)

## If this grows

- **Phrases, not just words**: the product is built around phrases (`NOTES.md`'s phrase entry: phrase → purpose → feeling → equivalents by formality → examples). Counting two- and three-word phrases ("you know", "I mean") is the obvious next step from word counts, and designing the phrase entry data model is an open to-do.
- **Backend**: when replies need to reach Claude (for Mai's replies, tagging purpose/emotion, or target-language equivalents), add Supabase serverless functions as planned rather than calling the API from the browser. Cache equivalents per phrase, and use the Batch API (50% off) where results don't need to be instant.
- **Routing**: the hash router in `useRoute.ts` is fine for a handful of flat pages. Switch to a real router when routes need parameters or nesting.
- **Mobile**: before wrapping in Capacitor, test dictation there. The Web Speech API behaves differently in iOS WebViews, and the original plan (keyboard dictation, no button) may be the better path on phones.

## Working conventions for this repo

- **No LLM features** (owner's decision, 2026-10-01; see `NOTES.md`). Features are rule-based and data-driven, from which-dialect's data (dictionary, pronoun table, picks, sentence frames, checker), with no API costs or LLM dependency. Don't propose AI rewrite buttons, LLM fallbacks or "needs AI" paths; when rules can't handle something, say so and fall back to hints. The planned Claude calls described above (the stack, AI-written Mai replies, the backend plan) are on hold: leave them as history, don't build on them.
- TypeScript everywhere, per the planned stack.
- **Record product decisions in `NOTES.md`** (the owner asks for this) and code-level details here. When a decision is reversed, say so in both, rather than silently deleting the old one.
- Every word counts in the top 100. Don't add filtering (nouns, stopwords) without the owner asking.
- Keep `FALLBACK_WORDS` and the Cheatsheet's top-100 list (`topWords.ts`) as the owner supplied them (the shorthand → dictionary-word replacements were the owner's call).
- Cheatsheet translations come from which-dialect: improve them in that package (and regenerate with `npm run cheatsheet`), not by hand-editing the JSON.
- Keep the POC client-side only until there's a concrete need for a backend.
- Before finishing a change: `npm run build` and `npm run lint` in `web/`, both clean.
- Test dictation changes in a real browser (Chrome and Safari at minimum); it can't be verified from builds alone.
